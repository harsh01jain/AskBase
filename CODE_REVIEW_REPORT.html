5.2 Role-Based Access Control (RBAC)

AskBase implements a 2-role RBAC system at the PostgreSQL database level, enforced via init.sql during container initialization.

RoleUserPermissionsUsed ForEnforced In
Read-Only nl2sql_reader SELECT only on all public tables All user-facing queries (natural language → SQL) init.sql, database.py
Admin root Full access (CREATE, INSERT, etc.) Audit logging, schema management, seeding docker-compose.yml, database.py

Security Controls Implemented

✓SQL Injection Prevention — validate_sql() uses sqlglot to parse and reject non-SELECT statements (INSERT, UPDATE, DELETE, DROP, ALTER)
✓Principle of Least Privilege — User queries run under nl2sql_reader which has only SELECT permission. Even if validation is bypassed, the DB role prevents writes.
✓Query Timeout — statement_timeout = 15s and idle_in_transaction_session_timeout = 30s prevent runaway queries and DoS.
✓Credential Separation — Database credentials stored in .env files, excluded from Git via .gitignore. Templates provided as .env.example.
✓Future-Proof Grants — ALTER DEFAULT PRIVILEGES ensures newly created tables automatically grant SELECT to the read-only role.
✓On-Premise Architecture — All data stays on the local machine. No external API calls for data processing. LLM runs locally via Ollama.
RBAC Assessment: The 2-role system provides defense-in-depth: even if the application-level SQL validator is bypassed, the database-level nl2sql_reader role prevents any data modification. Admin operations (audit logging, schema init) use a separate connection with elevated privileges, isolated from user-facing queries.
